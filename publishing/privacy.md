# Privacy facts for the Synergy notice

An inventory for writing the Synergy section of https://build40for40.com/privacy/, 5 November 2026. It describes the scaffold on `main` plus the plan on card 166. It is not a published policy. Re-check every line against the code before publishing, and don't claim anything that hasn't been verified.

## What the extension does on the device

- Asks for `storage`, `sidePanel` and one host permission: the Synergy service. It doesn't read the pages the user visits, run on other sites, or ask for `tabs`, cookies or history.
- Stores locally, in `chrome.storage.local`: the address of the Synergy service (`api`) and a random install id (`install_id`), sent with every request so each install's data stays its own.
- No sign-in for now (hand-distributed to invited people). WorkOS sign-in comes back before the store submission; describe it then.
- No analytics or tracking code in the extension.

## What it sends to the Synergy service (Cloudflare Worker + D1)

- **Profile ("About you"):** who the user is, what they offer, who they're looking for, and their search settings. The prototype adds the leads-a-day choice.
- **Feedback on each lead:** sent / not for me (with an optional reason) / reply outcome (call, rejected, no reply), each with a date, plus free-text notes.
- **Not sent:** browsing activity, page content, contacts, email or calendar data.

This is personal data, unlike the Naughty List, which only sent a website hostname. The notice needs a Synergy section that names the operator (40 for 40 Ltd) and contact (help@build40for40.com), and covers what's stored, why, how long it's kept, and how to have it deleted.

## Where the leads come from

Company, fund and partner information comes from Dealroom's licensed data. Partners' names and public profile links are personal data about people who aren't users. Keep to what Dealroom licenses for this use, and give a route for corrections.

The "why now" line for each portfolio company is planned to be generated by Claude from that company's figures and public news. Say so in the notice.

## Open before publishing

1. **Sign-in.** The API has no authentication on `main`, only a per-install id. Anyone holding an install's id can read and change that install's profile and feedback. Bring back sign-in first, then describe it (the provider, and what it shares with us).
2. **Retention and deletion.** Decide how long feedback and notes are kept, and how the user deletes their account and data.
3. **Cloudflare logging.** On Day 3 we checked the Worker's settings (no Logpush, no tail consumers, no observability). Repeat that check for `synergy-api` once it's deployed. Don't promise a Cloudflare retention period.
4. **Dealroom terms.** Confirm that showing partner names and links in a client tool is within the licence.

Don't write "we collect no data" or "everything stays on your device". Neither is true for Synergy.
